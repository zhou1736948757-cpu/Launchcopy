## Problem
AppDelegate substitutes InMemoryAppearancePreferencesStore when the failable persistent-store constructor returns nil. That replacement returns Saved, causing edited controls to advance committed/presented values without any persistent owner. The equal/default no-op shortcut can also report applied. Normal native UserDefaults success/restart evidence does not cover this exact factory failure; the real-machine incidence of nil is unmeasured.

## Bounded design
Add a synchronous internal persistent-store factory argument to existing AppDelegate.installAppearancePreferences, defaulting to the same dedicated/profile suite constructor. Explicitly injected stores retain precedence and never invoke that factory. First extract this seam without changing fallback behavior and run a causal actual-controller regression with factory nil; do not count missing-symbol compilation as RED.

On factory failure, establish no appearance settings coordinator rather than a successful in-memory substitute. Preserve already accepted displayed/queued preferences; initial startup still uses defaults. Configure the existing view with no Apply callback, so its existing translated AppearanceUnavailable handler rejects both edited and unchanged/default Apply, keeps the draft and never presents/saves new preferences. Reuse existing failure presentation; no enum/resource/schema changes or false corrupt-data message. Dismissal discards only the unavailable draft back to the last accepted queued-or-displayed snapshot. Weak/current-view/no-current-coordinator guards reject retained obsolete discard callbacks after owner/view replacement. Healthy persistent/injected-store paths retain their behavior.

No automatic same-process store retry is introduced; a normal new startup can use an available store. Do not add a global permission prompt, synchronous flush/fsync guarantee, fallback to production data, silent session-only feature or a native fault-injection flag just to obtain a screenshot.

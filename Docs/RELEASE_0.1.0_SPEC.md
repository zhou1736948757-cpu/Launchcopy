# Launchcopy 0.1.0 direct-distribution release specification

## Authorization and outcome
The user requested an official GitHub release and explicitly chose distribution without Developer ID signing/notarization. Prepare a normal-production-identity macOS application from the uploaded L1 snapshot; do not re-label the isolated preview bundle. First stable GitHub release: v0.1.0, build 1. This is a user-directed release designation, not proof that every device, long-tail hitch, installation path or reference-rights question is closed.

## Scope and non-goals
Source baseline: e13125b3f9a68380b4c24ef585d31cbc7ddc4942; parent implementation 049fe95e9071421b19c7a02980bf5b974c33e057. Native SwiftPM/AppKit; macOS 14+, initially Apple Silicon arm64 only. Keep product code and paging parameters unchanged. Use Launchcopy / com.launchcopy.app, ordinary production defaults and stores. Do not carry UI-test/integrated-preview/gesture-validation markers, profile data, local telemetry opt-ins or preview capability restrictions into production packaging. No automatic migration of preview layouts, overwriting installed apps, restart of existing apps, system-security changes, arbitrary license selection, reference assets, notarization, account changes or paid services.

## Architecture and publication
Export the exact Git commit to a unique build-only workspace. Keep the original main checkout, index and dirty work intact. Build and test only the export; retain logs outside distributable assets. Existing packaging script constructs a unique bundle. No deliberate code signing; inspect and report any compiler/linker ad-hoc executable signature accurately, never as Developer ID or Apple approval. Package a clean ZIP with Launchcopy.app only, a SHA-256 file, installation/known-limitations notes and source provenance. Repository release documentation is a separate auditable follow-up commit; executable source paths must remain identical to the checkpoint. GitHub Release uses an immutable v0.1.0 tag targeting that verified source, draft until assets and details are checked, then stable/non-prerelease. Update remote main only with an inspected fast-forward/expected-head check; never force. If authenticated release/asset publishing is unavailable, retain a complete local package and report the exact missing access, not a fabricated Release.

## Verification and acceptance
1. Fresh unfiltered tests execute all tests with zero failures; report actual count and warnings. Review production entry defaults separately from the prior preview-only physical acceptance.
2. Clean Release build/package succeeds. Mach-O is arm64, deployment target and bundle version/identity are correct; all three languages resolve from packaged resources independently of development fallback.
3. Packaged application passes resolver-only startup checks without initializing UI, preference stores, real app actions or telemetry. Normal identity is not isolated/windowed; disabled test/diagnostic metadata absent. Run persistence/termination/activation/production admission regression tests as part of the full suite; do not equate them with an in-place production upgrade or fresh-device GUI test.
4. Inspect ZIP path safety, exact contents, privacy/credential/raw-data exclusions, linked runtime dependencies, source commit and resource/executable/archive checksums. No private data or build manifests with absolute local paths inside the ZIP.
5. An independent read-only reviewer audits production entry/distribution safety and explicit evidence limits; Main integrates findings before publication. Maximum three active agents including Main; all writes disjoint and no concurrent builds/tests.
6. Remote tag, Release status and uploaded asset size/hash/content must be read back. A local ZIP or source branch alone is not a published downloadable release. Never bypass Gatekeeper; document Apple's supported per-app approval route and security warning honestly.

## Risks and maintenance
No usable Developer ID identity was found; not notarized and may be blocked on download. Apple Silicon only until separately built/verified for Intel. Private MultitouchSupport integration can change across OS versions and has no App Store compatibility claim. No blanket licensing/clean-room/legal-clearance claim; retain provenance and do not invent a license. Production-mode first launch or upgrade GUI tests require a safe isolated environment; do not run against the user's real stores. Long-tail timing and other hardware remain unproven. If a material release blocker is found, fix only with an explicit bounded source/spec change, rerun affected gates and update hashes; do not ship a known data-loss defect just to finish. Release artifacts remain immutable; later fixes increment the version.

## Verification correction — test-only bounded wait
The first fresh export suite executed 3824 tests with one failure in AppSourcesProfileAssemblyTests.testActualOwnerRevalidatesFixedProfileRootAfterReplacementAndRecovery: the helper exhausted 1000 Task.yield calls after roughly 90 ms. Five unchanged focused runs subsequently executed 5/0 each; that does not erase the first failure or certify its exact production cause. The source path intentionally awaits off-main admission and catalog work; a yield count gives no scheduler time guarantee. Replace only that test helper with a five-second ContinuousClock deadline and cancellable 1 ms suspension, preserving every safety predicate/assertion and reporting the actual call site. No product implementation, public contract or paging parameter changes. Fresh post-repair focused repetitions and full suite remain required; the release source commit must include the exact test-only diff. The requested write-swift skill path was unavailable; no skill content was assumed.

## Release-blocker repair authorization — B1 production layout fallback
Independent source review found that a production Application Support resolution error selects the shared temporary root and broad `.tmp` cleanup can delete unrelated items. Main authorizes a bounded safety repair under the release's no-known-data-loss rule, superseding the earlier unchanged-product-only plan solely for this defect. Replace fallback I/O with an explicit unavailable/read-only LayoutStore and a neutral storageUnavailable reason; retain the existing normal store path, schema and Quit protection. Inject the directory provider at the composition seam for safe tests. No real temporary root, production store or user app may be used for reproduction. Narrow journal cleanup to the two exact owned slot temporary filenames, only while holding the store lock, and never recursively remove directories or follow symlinks. Missing directories/locks must not broaden deletion. Tests must preserve unrelated file/directory/symlink sentinels, prove failure-path zero journal/lock writes and truthful read-only load/enqueue/flush/reset/Quit state, and preserve ordinary persistence/recovery. App launching remains available; workspace mutations are denied by existing read-only guards. This release's fresh baseline/commit/artifact hashes must include the repair; L1 preview acceptance is historical, not automatically reissued for the repaired binary. Product behavior outside storage failure/cleanup and accepted paging parameters must remain unchanged.

## Packaging correction — local ad-hoc resource seal only
The fresh compiler output already contained an automatic linker ad-hoc Mach-O signature (no authority/team, Info.plist not bound, resources unsealed). Bundle assessment reported a resource-structure error rather than merely an unidentified developer. Interpret the user's selected route as **no Developer ID identity/no notarization**, not permission to ship a structurally invalid bundle. This explicitly supersedes the earlier specification's no-deliberate-signing implementation detail: copy the owned generated bundle to a new candidate, add only a local ad-hoc resource seal (`codesign --sign -`, no certificate, no timestamp, no hardened-runtime change), verify code/resource integrity, and repeat all final artifact checks. Do not touch the original bundle/ZIP, installed apps, Keychain credentials, entitlements, system protections or source freeze. Keep stating no Developer ID signature/notarization; disclose the ad-hoc seal is not identity verification/Apple approval. Gatekeeper rejection is expected but must no longer be treated as success if it reports malformed signature/resources. New executable/archive hashes and sidecars are required.

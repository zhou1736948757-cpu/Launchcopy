## Finding F1 — [P2] Rearm the policy when accepted Library writes finish

**Location:** `Sources/PagingPrototypeApp/AppDelegate.swift:2635` (new admission condition), with missing event delivery in `Sources/PagingPrototypeApp/AppLibraryOwnerController.swift:225-239`.

**Evidence / trigger:** Save an identifier-search choice while `appLibraryOwner.preferences.pendingCount > 0`, and allow its one scheduled attempt to run before that Library write completes. The attempt resets `identifierSearchRetryScheduled` at AppDelegate:2651, then returns at :2658 because :2635 rejects it. When the last accepted write completes, `AppLibraryPreferencesCoordinator.swift:61-78` decrements the count and calls its existing `onChange`; the owner routes that to `preferencesChanged()` (:55). That method renders settings, handles category receipts, refreshes projection if open, and refreshes entry state, but never calls `onReadinessChange()` (:225-239). Neither `AppLibrarySettingsView.applyState` nor `categorySaveDidComplete` emits the missing notification. The AppDelegate bridge at :2270-2273 therefore does not rearm this pending policy.

A concrete case requires no open Library editor: keep an accepted Library enable/save outstanding, switch to app management and save identifier search, let the scheduled attempt be rejected, then complete the Library write while no other lifecycle/text/menu event occurs. Pending storage remains accepted, effective matching stays on the old policy, and the checkbox continues to report queued until an unrelated event eventually retries it. An open successful category-save completion can have the same gap. This violates the promised application after the blocking operation finishes.

**Likely root cause:** The new guard depends on Library writer readiness, while the reused readiness callback currently represents view ownership/close events rather than writer completion.

**Recommended solution:** Notify the existing owner readiness bridge when Library preference/write state changes, at least when the final pending write reaches a terminal outcome. Continue scheduling onto the next main turn; do not add polling or bypass the writer guard. Add a held asynchronous Library-store integration regression that rejects the first scheduled policy attempt, releases the write, and observes application without calling `flushPendingIdentifierSearchIfReady`, manually scheduling a retry, or injecting an unrelated notification.

**Affected scope / regression risks:** Library preference completion -> AppDelegate policy scheduling and queued/applied receipt. Cover success and failure, Library closed/open, and stale completion after teardown. Preserve accepted-write ownership, generation checks, and no interaction cancellation.

**Confidence:** High for the missing source event; no runtime reproduction was attempted. Main's reported passing Library integration test does not exercise this writer boundary.

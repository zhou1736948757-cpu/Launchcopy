## Recommendation for the design now under consideration

**Prefer detached first-viewport layout plus a small, sequential, cache-only icon preparation job. Keep bitmap drawing optional and separately measured.** Main's proposed ephemeral card/image draws can exercise additional application-side drawing, but do not establish within-window blur/compositor realization. Preserve the existing single-use inert pool and live binding rules. Never make entry wait for warm-up completion.

The proposed separate `WarmupKey(bounds, scale, appearance)` needs two additions: accessibility material policy and association with the particular prepared pool/content generation. A presentation environment key alone cannot establish that a replacement pool's new controls have been laid out/drawn. Layer backing should be prepared once for actual missing grid chrome, preferably at construction; most named grid chrome is already explicitly layer-backed.

### Concrete hazards and bounded alternatives

| Proposed operation | Concrete issue | Recommended bound or simpler alternative |
| --- | --- | --- |
| First-viewport card layout | Prepared cards start at zero frames and are outside the gallery document. `gallery.cards` is empty during preparation, so normal gallery layout does not lay out the private pool. | Use `LibraryGalleryGeometry` with the intended **gallery viewport**, assign frames to private never-presented cards, and explicitly lay out only intersecting cards. Do not call live `apply`, attach to the document/window, or call live icon synchronization just to obtain layout. |
| One `cacheDisplay` into a <=512 x 512 bitmap per yield | A point-space bound is not a pixel-allocation bound. At maximum card width, a complete card is 248 x 280 pt, or 496 x 560 px at 2x; including its caption exceeds 512 px vertically. An automatically allocated representation can also use a detached view's unsuitable backing scale before a later clamp. | Bound the actual representation's `pixelsWide` and `pixelsHigh` before allocation. Preserve the mapping between point-space bounds and pixel-space size. Prefer layout alone initially; otherwise use one disposable explicitly bounded bitmap, with documented resampling/clipping, and never retain it as displayed content. A 512 x 512 RGBA buffer is approximately 1 MiB of pixel storage, not a bound on all AppKit temporary allocations. |
| Drawing the whole detached category card | Its `.withinWindow` material is inactive and has no actual window backdrop. A successful bitmap operation is not evidence that native blur, live layer textures, or WindowServer work is warm. It may only render a fallback. | Keep material inactive; treat the operation as a bounded CPU/native-control drawing attempt. Do not activate, temporarily mount, order, or create a hidden/transparent window to make blur render. Do not substitute a cached card bitmap for the live material. |
| Exact 88/40 pt icon prefetch and transient image draw | Exact-size keys are correct, but the loader ignores size/scale and obtains the system image; the pipeline caps it independently of the requested size. Cache insertion does not universally force all image representations to decode. | Use the existing shared pipeline and the current destination scale. Draw the delivered image only into a disposable, bounded graphics context on MainActor. Do not change the cached `NSImage.size`, representations, or cache policy. Treat the draw as exercising one selected representation, not proof that every representation/GPU upload is ready. |
| Sequential pipeline requests | `request` returns immediately. Sequentially issuing requests in a loop still queues many loads unless each completion is awaited. Cancellation cannot interrupt a synchronous `NSWorkspace` load or bitmap draw already executing. | Keep at most one idle consumer outstanding; await its completion before issuing another. Recheck admission, content/pool generation and environment both after completion and immediately before drawing. Stop scheduling on real input. Cancel only idle-owned handles, never shared `cancelAll(for:)` or `purgeAll()`. |
| A separate environment-only warm-up key | Same bounds/scale/appearance can describe a newly constructed pool. Reduce Transparency and Increase Contrast can change without a different appearance name. Detached `window` is nil, so a fallback scale of 1 would warm different keys than a 2x destination. | Associate render readiness with pool/preparation generation **and** existing projection validity. Include the current transparency/contrast policy, actual destination scale and effective appearance. Use stable target viewport/pixel geometry; do not key on animated offsets or global window position. Recheck all of these across every suspension. |
| Preparing grid chrome layer backing in a production idle callback | Many targets already set `wantsLayer = true` during construction. Conversion of a remaining attached visible view can itself invalidate/redraw it. Layer creation does not prove backing textures or first-return rendering are ready. | Count actual previously unprepared targets. Prefer a one-time construction-time assignment for a demonstrated missing view; otherwise use the existing idle admission with implicit actions disabled and preserve frames, transforms, opacity, colors, hidden state and search ownership. Keep backing for that view's lifetime; do not toggle it per direction. |

## Icon/cache/decode lifecycle and what remains cold

1. **First visible gallery layout still establishes geometry and starts icon work.** `AppLibraryGalleryView.swift:191-219` sizes the scroll/document/cards and calls `synchronizeIcons`. Admission requires a visible window, no hidden ancestor, and a card intersecting the document viewport. Only then does it apply visible material policy and request icons. `LibraryCategoryCard.layout` separately computes panel/material/caption/button frames at `313-335`. Preparing that layout in advance can move this specific work; it does not remove live viewport reconciliation.

2. **Gallery, result-list and grid variants are distinct cache entries.** Gallery buttons request 88 pt or 40 pt at the actual window scale (`AppLibraryGalleryView.swift:442-444`). List rows request 32 pt (`AppLibraryView.swift:977-978`). The ordinary grid's default is 48 pt (`Sources/PagingPrototypeApp/AppCatalogAssembly.swift:413-416`; `Sources/AppGridUI/AppGridPageView.swift:356-360`). `Sources/AppIconPipeline/IconKey.swift:16-30` includes identity, point size, scale and `.system` appearance, with no catalog revision. A warm grid does not itself establish gallery cache hits. There is no cross-key merge in this pipeline; system-internal icon caching is outside this source evidence.

3. **The pipeline loads, caps and caches, with a partial decode boundary.** `Sources/AppIconPipeline/IconLoading.swift:31-36` calls public `NSWorkspace.icon(forFile:)` or the generic application icon; it does not use the requested size/scale. `IconPipeline.swift:387-403` loads and invokes `cappedImage`; `479-514` rasterizes oversized images into a bitmap intended to be <=256 px per side, but returns already-small images unchanged, and returns the original image if target allocation/context creation fails. Thus some successful cache entries have undergone bitmap drawing; cache insertion is not a general eager-decode guarantee for all images/representations. Estimated cost is the largest representation's width x height x 4, not measured resident memory (`456-468`).

4. **Cached images still require delivery and live drawing.** Hits queue a MainActor callback (`IconPipeline.swift:238-268`, `436-445`), and the button assigns `image` later after serial/key/generation/visibility checks (`AppLibraryGalleryView.swift:450-458`). `iconDelivery` measures that callback/assignment block, not loader/decode or the later control draw. A prefetch callback must not populate detached buttons, create an `AppLibraryActionRequest`, or become a new live snapshot path.

5. **Hide/return cancels local requests and clears button images, but does not purge the shared cache.** `AppLibraryGalleryView.swift:204-206`, `433-439`; `AppLibraryView.swift:342-363`, `948-950`. `AppLibraryView.apply` also increments presentation generation and cancels/rebuilds gallery bindings (`240-262`); reset revokes all cards and content (`265-289`). Consequently a later gallery display still performs request/assignment/draw work even if its exact image keys remain cached. A new session or reset may also need a fresh never-presented pool.

6. **First return to the grid is not established cold by these findings.** The assembly shares one pipeline with its renderer (`AppCatalogAssembly.swift:617-630`). Gallery preparation neither primes the grid's different 48 pt keys nor proves that the already displayed grid lost its images/cache. Conditional grid rebinds still call `requestIcon` (`AppGridPageView.swift:263-272`, `406-426`). Whether a particular return rebuilds/reveals that grid belongs to Main's owner/navigator investigation. Do not add a second full-grid prefetch based only on the reported symptom.

7. **Cache warmth can legitimately disappear.** Defaults are 256 entries / 64 MiB estimated cost / four concurrent loader calls (`Sources/AppIconPipeline/IconCache.swift:9-20`). Count/cost LRU eviction occurs at `64-80`; memory pressure clears cached entries (`IconPipeline.swift:448-453`). Committed mapping changes invalidate affected identities across all variants, in-flight ownership and queued deliveries (`AppCatalogAssembly.swift:683-688`; `IconPipeline.swift:313-335`). There is no automatic expiry timer in the pipeline; `purgeExpired` is explicit. No new persistent cache, global purge, larger limits or invalidation bypass is justified here.

8. **The loader permit is not a bound on all queued/drawing work.** `IconPipeline.swift:51-75` has a continuation-based semaphore without a cancellation-aware wait removal. The permit encloses `loader.load` only; capping happens afterward (`390-395`). A canceled queued task can still reach non-cooperative loading/capping. The load-ID check rejects a retired result at publication (`414-426`), but does not recover spent CPU work. An idle prefetch should therefore enqueue one request at a time and retain its worker ownership until cancellation actually settles.

## Material, appearance and action correctness

- `AppLibraryGalleryView.swift:260-262` configures a native `.popover`, `.withinWindow` effect. Preparation changes it to inactive through `applyMaterial(visible: false)` (`115`, `373-375`). Its first live activation and real backdrop composition remain outside existing detached preparation. Avoid describing a detached `cacheDisplay` success as material/GPU warm-up.
- `applyMaterial` uses **this card's** effective appearance (`359-363`), plus Reduce Transparency / Increase Contrast (`343-346`). A solid fallback hides the effect and uses current dynamic colors/border policy (`356-375`). The implementation already avoids rewriting equal effective properties. Preserve that behavior; do not freeze a detached appearance override or force the blur visible to make a bitmap attractive.
- Effective-appearance callbacks reapply material policy (`338-340`); accessibility-display changes trigger gallery synchronization (`75-78`). Private prepared cards are outside that live iteration, so warm-up validity must handle policy changes and normal live application must still reconcile them.
- Bitmap output must be disposable and never assigned to the live panel's `layer.contents` or used as an overlay/snapshot transition. That would replace a live backdrop with an incorrect frozen rendering and introduce a new visible handoff.
- Preserve passive card backgrounds/captions and individual app/miniature actions. Fresh activation remains guarded by `AppLibraryView.swift:636-646` and the gallery's binding revision. Never invoke `performClick`, accessibility press, focus APIs, window ordering, or live snapshot application as a preparation technique. Draw the private card, not the root/search/header hierarchy.

## Required refinements to Main's proposed warm-up key/job

These are recommendations for Main's implementation/specification; none were implemented by this audit.

1. Keep existing projection `PreparationKey` authority unchanged. Associate additional render readiness with **pool identity/preparation generation + projection validity + stable target viewport/pixel size + actual display scale + effective appearance + Reduce Transparency/Increase Contrast**. Bounds/environment changes should revoke render readiness, not unnecessarily rebuild an otherwise valid immutable projection/card pool.
2. Keep one current task, a finite first-viewport card budget and a finite distinct-icon budget. A conservative initial icon cap is 28 exact keys (at most four full seven-icon cards), ordered by destination visibility. At intended 256 x 256 RGBA normalization this is about 7 MiB of estimated icon pixel cost, **not** a guaranteed resident-memory bound. Warming all 154 possible buttons would approach 38.5 MiB estimated cost before grid/list variants and could evict return-grid entries. Existing 64 MiB/256-entry limits remain authoritative.
3. Yield/check before each card operation; keep each synchronous layout/cacheDisplay/image draw separately bounded. A yield is an opportunity to process input, not an idle-time deadline or cancellation point inside a draw. Recheck after every suspension and before publishing completion. Cancel on the existing readiness/visibility/edit/write/lifecycle gates, without new timers or drawing from scroll dispatch.
4. On pool consumption, stop working on those view objects immediately. Normal live entry must be able to consume the pool before bitmap/icon work finishes. A late completion must neither draw newly presented controls nor mark a replacement pool ready. Pure image results may remain in the existing cache only through its ordinary current-source publication rules.
5. Keep idle pipeline handles/continuations separate from button handles. Completion must resolve cancellation/failure exactly once, even when source invalidation suppresses a queued callback. Merely awaiting an onApply callback is unsafe: pending-consumer cancellation and `invalidateSources` can intentionally produce **zero callbacks** (`IconPipeline.swift:283-335`, `436-444`). Do not hold the single worker slot forever waiting for such a callback. An explicit cancellation completion path is required.
6. Do not assume `handle.cancel()` revokes a callback already marked delivered. Consumer state changes to delivered before MainActor admission (`238-242`, `424-425`); cancel is then a no-op (`104-118`, `283-284`). Warm-up callbacks need their own current-job/environment checks even after handle cancellation. Do not retry failures immediately on every idle notification; bound attempts for an unchanged key and report partial completion truthfully.
7. Keep bitmap lifetime within the synchronous step, restore graphics state/context on every exit, and do not retain bitmap arrays or mutate shared cached images. A bitmap that was allocated/drawn successfully only supports a component-work counter. Record layout, card draw, icon hit/miss/load/draw, cancellation and actual new layer-backing counts separately; never add nested durations as CPU time or hardware frame latency.

## Grid chrome layer preparation: source-specific limits

The production grid-view list is `Sources/PagingPrototypeApp/AppDelegate.swift:2930-2932`: surface, dots, Settings button, space notice, catalog status, and the optional entry button. That list is a source pointer, not an assertion that every member currently exists or needs conversion.

Several members are already explicitly layer-backed before a first Library transition:

- Root/container and surface: `AppDelegate.swift:650-668`.
- Page dots: `Sources/PagingPrototypeApp/PageDotsView.swift:98-106`.
- Settings button: `AppDelegate.swift:3869-3872`.
- Catalog status view: `Sources/AppGridUI/AppGridStatusView.swift:36-50`.

Therefore a blanket idle `wantsLayer = true` assignment does not demonstrate useful new work. Main should identify/count the actual remaining conversion, without recursively forcing backing on every native descendant or changing status visibility/text. If a lazily created chrome view arrives after a once-only preparation flag, its construction must establish the same backing invariant; a global once-ever flag must not silently miss replacement views. Conversely, parent navigation/reset must not undo backing and recreate the cost on first return. Exact presentation behavior remains Main's investigation.

The simpler source fix, where appropriate, is to make the demonstrated missing view layer-backed in its existing initializer before insertion. If a production idle callback is used, it must not open the launcher, change key/responder ownership, expose the stationary Library header, animate opacity/transform changes, or use `display`/window ordering to prove readiness. Native no-flash and first-return acceptance remain pending even if layer creation is verified by counters.

## Prioritized concrete findings (four)

### 1. [P2] A queued accepted activity write can disappear when its coordinator is released

**Evidence:** `LaunchActivityCoordinator.swift:189–215` retains the newest queued document only in `pending`. The active task captures `self` weakly at 201, saves the current immutable document at 202, then requires a surviving coordinator at 203 before starting the queued write at 214. `invalidate()` at 235–239 suppresses presentation but provides no independent queued-write owner. This differs from `MainGridCapacityCoordinator.swift:88–109`, which retains its accepted-write owner until the queued handoff completes.

**Concrete trigger / effect:** suspend an older activity save; accept a Clear or privacy-OFF snapshot behind it; invalidate and release the last external coordinator reference; finish the older save. The first captured save can finish, but the weak guard prevents the queued Clear/OFF from ever reaching storage. Normal hiding with a retained owner is not this trigger. The source demonstrates a lifetime gap; no current production data loss is asserted.

**Bounded fix:** retain the activity accepted-write owner across each actual save and queued handoff, releasing it when the finite active/pending chain settles. Keep `isActive` guards on callbacks and refuse new admissions after invalidation. Preserve activity-specific privacy/clear/coalescing semantics; do not replace the coordinator with a generic store queue. A deliberately stalled injected save may then retain the writer until its receipt, as the accepted-write contract requires.

**Future regression acceptance:** extend `Tests/PagingUITests/LaunchActivityCoordinatorTests.swift` with a suspended fake, an older save plus queued Clear/OFF, and a weak reference to a coordinator whose strong external reference is dropped after invalidation. Release receipts and verify both intended documents reach the fake in order, callbacks remain suppressed, and the owner eventually deallocates. Existing clear/OFF tests at 122–138 and 283–307 retain the owner and do not exercise this release boundary.

**Defer:** application-wide owner-replacement/quit orchestration remains Main's work; no change to on-disk activity schema or history policy.

### 2. [P2] A catalog winner can change without invalidating its cached icon source

**Evidence:** `AppCatalogCore.swift:56–61` derives `IconIdentity` solely from AppID. `IconKey.swift:16–30` adds size/scale/appearance, not source incarnation. `IconPipeline.swift:234–236` returns a cached image before invoking the resolver. `AppCatalogAssembly.swift:582–588` rebuilds resolver URLs on commit but does not invalidate cached/in-flight source content; `replaceScanRoots` at 648–662 deliberately retains the pipeline. The only production definitions/calls found for `purgeAll`/`purgeExpired` in this slice are the pipeline methods themselves (`IconPipeline.swift:304–317`).

**Concrete trigger / effect:** first cache the icon for bundle-ID X at path A; change admitted roots so the same bundle ID's selected record is at B; request the same size/scale/appearance. The stable key still hits A's image even though the new resolver maps X to B. UI generation checks cannot detect this: the cache hit is delivered with the *new* consumer generation. Same-path app updates are another freshness question, not proven resolved here. AppDelegate was not inspected: Main must check any separate compensating invalidation there before treating this assembly-level gap as an integrated production failure.

**Bounded fix:** define source-change invalidation independently of catalog revision. At minimum detect selected identity-to-URL changes on committed catalogs, invalidate affected cached entries and retire their old loads before rebinding. Fence old completions using the existing loadID mechanism. A plain cache purge is insufficient if an older in-flight load can repopulate it. Keep public key descriptions redacted; do not add raw paths/hashes to telemetry or invalidate on every search/page presentation.

**Future regression acceptance:** with an injected loader/resolver, cache A, commit the same AppID at B, and verify a subsequent current request loads B. Repeat with A's loader held until after invalidation to verify it cannot overwrite B or consume its new listeners. Keep unaffected identity hits and ordinary cache reuse unchanged.

**Defer:** same-path content incarnation policy, multi-instance identity redesign and NSWorkspace caching behavior need separate decisions. No runtime image error or speedup is claimed.

### 3. [P2] Diagnostic getters bypass the synchronization used by their writers

**Evidence:** `CatalogRepositoryDataSource` is explicitly `@unchecked Sendable`. Its duration properties are plain stored public getters (`AppCatalogAssembly.swift:91–94`), while `store(outcome:)` updates them under its lock at 177–188. The real bridge reads both directly at `PagingTelemetryBridge.swift:153–158`; another async refresh can update them concurrently. The snapshot getter correctly uses the lock at `AppCatalogAssembly.swift:104–112`. A related exposed API gap exists in `TelemetrySession.swift:29–62`: public stored diagnostic properties bypass its queue, whereas mutations in `record`, `end`, register methods and `recordLocked` are queue-confined (for example 104–120).

**Effect / boundary:** locking writes alone does not synchronize plain external reads. Duration reads can race and can describe different refreshes; the telemetry session's documented thread-safety similarly does not extend to its public stored getters. The data-source bridge is a concrete consumer; concurrent external reads of every telemetry-session property have not been established.

**Bounded fix:** use private backing state and synchronized diagnostic snapshots/getters in each existing owner. Read the paired scan/refresh durations together. Inside the telemetry queue use backing values directly, avoiding nested `queue.sync` deadlock. Keep the two owners' different synchronization strategies; no shared lock/queue framework is needed. This fixes access synchronization, not attribution of an arbitrary later refresh's timings to a historical presentation revision.

**Future regression acceptance:** Main can add bounded concurrent refresh/diagnostic reads using injected scanners and concurrent telemetry record/state snapshot reads; verify coherent pairs and no deadlock. Use a race-detection run if available in Main's serialized verification phase. Do not add per-frame heavyweight status aggregation.

**Defer:** immutable per-revision timing receipts and asynchronous/buffered telemetry are separate contract/performance changes. The current enabled telemetry writer performs synchronous I/O; its cost was not measured here and is not evidence for the user's first-swipe hitch.

### 4. [P3] Reusable JSON inspection is coupled to the Library feature's concrete store

**Evidence:** `AppLibraryFileStore.decode` calls `hasDuplicateObjectKeys` and `rootVersionTokens` at `AppLibraryStore.swift:192–204`; those lexical functions live on that concrete actor at 217–296. `LaunchActivityFileStore.decode` reaches into the Library actor's static namespace at `LaunchActivityStore.swift:70–83`. These are **two actual same-contract consumers**: bounded UTF-8 input, escaped-equivalent duplicate-key detection, and root-only schema-token collection. Their subsequent v1 header classification is also currently the same, but their bodies and recovery outcomes remain separate.

**Effect:** a change to a reusable data-admission primitive appears feature-local and obliges another feature to depend on an unrelated concrete persistence implementation. It is an ownership/maintenance issue, not evidence that the existing helper misparses accepted input.

**Bounded fix:** mechanically move only the two existing lexical functions to a small internal Foundation-only JSON inspection namespace and update both consumers. Preserve exact behavior and keep final schema classification, supported versions, limits, recovery decisions and result enums in each feature. No public API widening or new target/dependency is necessary.

**Future regression acceptance:** Main should run the existing Library and Activity store tests, particularly escaped keys, duplicate root/nested keys, future/ambiguous headers, nested header-like strings, non-UTF-8 and protected-byte preservation during explicit recovery. Structural acceptance requires both real stores to use the new namespace and no remaining Activity dependency on Library's concrete decoder helpers.

**Defer:** `MainGridCapacityStore.swift:77–173` additionally detects unknown keys and protects noncanonical schema tokens differently; `LanguagePreferences.swift` supports UTF-16/32 normalization and different future-version results. Do not merge those policies. `LocalAppLibraryFileIO` is already shared by Library/Activity/Capacity, but its directory locking, expected-byte comparison and post-rename receipts require a separate contract review before renaming/generalizing it. UserDefaults acknowledgments must not become file-flush receipts.

## Closed Library precomputation/cache advice — Main-owned follow-up

The new physical feedback says the **first Library swipe still hitches**. That feedback remains authoritative; this source audit neither reproduces it nor identifies its dominant cost. The blue-frame change is entirely Main's UI scope. During report closeout Main began adding preparation to the Owner controller; the advice below describes required safety boundaries and is not a review of that new implementation.

**Baseline service seam (before Main's concurrent preparation changes):** `AppLibraryProjectionController.swift:57–78` only accepts updates while open and clears/cancels on close. `startNextIfNeeded` at 81–100 already bounds projection work to one active plus one replaceable pending request. The request at 6–31 captures catalog, management, Library preferences, query/category, locale, activity document/section and clock. `AppLibraryOwnerController.swift:348–355`, 409–428 and 471–478 currently refresh projections only when open. Entry creates the view at 160–203; therefore warming this pure projection seam alone cannot establish that view construction, layout or icon delivery costs have been removed.

A safe first option is **one private, closed-state precomputed default projection**, scheduled after a committed catalog/preferences/management/locale change outside the swipe/event stack. It must never open the projection controller, publish its actionable `snapshot`, render a view, mint action requests, collect activity, perform disk writes or make the closed Library accessible. Retain the existing one-worker/one-latest-pending bound; speculative work must not create an independent queue competing with open requests. Skip unnecessary warming when the feature is disabled or input admission is unresolved.

At entry, build the authoritative immutable request again and promote a candidate only if its complete input key still matches: owner/assembly epoch plus catalog revision, management values, committed Library values, locale, and the entry query/category. Catalog revision alone is insufficient. Compare bounded values or explicit generations maintained by their actual owners; do not compute a large content digest on the gesture callback. Cache only one candidate (or a clearly bounded small set), memory-only. A miss follows the existing async projection path.

**Prefer initially excluding activity sections from speculative results.** A static base projection may be reusable while activity ordering is recomputed from current consent/document/time at entry. If an activity result is cached, its key must include activity contents/receipt-relevant state and the time boundary used by the rolling window. `activity.generation` alone is insufficient because recording mutates the document without necessarily changing that admission generation. Clear, privacy OFF, Library OFF, recovery, changed history, and time-window rollover must revoke any candidate before promotion.

Source replacement (`AppLibraryOwnerController.swift:330–337`), failed refresh, hidden/alias changes, preference receipts, language changes, close/reopen and teardown must invalidate or re-key candidates. Keep public `snapshot == nil` while closed/updating. Preserve all action checks in `resolve` at 393–401: active/open/non-preview state, no pending preference writes, source validity, readiness, action generation, current catalog revision, current canonical URL, hidden policy and current snapshot membership. A cache hit grants no independent action authority. A fresh open session must mint fresh action generation even if it reuses immutable projection content.

**Future acceptance for Main:** hold an injected projection across close/open; mutate each key input; deliver old results after source invalidation and failed refresh; perform Clear/OFF and time rollover; verify no closed snapshot/action can execute, stale candidates miss, and matching candidates promote once without extra workers. Any claimed hitch improvement requires matched first-entry evidence on the candidate and renewed physical/user acceptance. Rendering, retained AppKit views, pre-mounted geometry and focus-ring behavior remain Main's separate work.

## Boundaries worth preserving and larger deferred work

- Stable AppID, persistent references, source-path identity, icon content identity and action eligibility are different contracts. The root-priority default is not interchangeable with `keepMultiInstance`; do not widen multi-instance support in this wave. Catalog cancellation rejects partial snapshots; data-source configuration generations reject obsolete source results.
- Workspace persistence tracks submission/epoch and actual flush outcomes (`WorkspacePersistenceQueue.swift:61–113`); quit keeps an exactly-once generation-gated decision (`WorkspaceQuitCoordinator.swift:17–59`). Activity has privacy admission and clear barriers; Capacity coalesces intentions; Library persists ordered captured drafts. Similar polling loops do not justify one generic coordinator.
- File-backed stores preserve no-follow/pinned-directory/compare-under-lock behavior and distinguish protected payloads from explicit corruption recovery. Post-rename fsync failure can be indeterminate; an equal-value retry must still obtain a real receipt. Keep UserDefaults `.saved` at acknowledgment strength, as documented in `LanguagePreferences.swift`, rather than treating it as restart durability.
- Localization resource snapshots and typed integer templates are suitable reusable boundaries; retain packaged-only lookup, bounded reads, fallback and raw-resource validation before fallback masks missing keys. A broader key registry/fallback redesign or exact key-count policy change is not needed for this wave.
- Native touch backend, global shortcut, wallpaper caching, whole-process callback isolation and all Main-owned UI composition need deeper dedicated review if selected later. Inventory coverage is not proof of lifetime or performance safety. No exhaustive claim or previous physical acceptance is transferred to future changes.

## Blocking finding

### B1 — [P1] Failed production storage resolution can delete unrelated temporary items

**Finding.** An ordinary production startup whose Application Support directory resolver throws falls back to the *entire* `FileManager.default.temporaryDirectory`. Opening the layout store then enumerates that directory and deletes every immediate child whose name ends in `.tmp`, without checking that Launchcopy created or owns the item. The concrete deletion API also accepts directories. This is an unintended data-loss path affecting other applications' temporary work; it does not require a removal confirmation, a layout mutation, telemetry, or a test/preview marker.

**Exact evidence and trigger chain:**

1. `Sources/PagingPrototypeApp/AppDelegate.swift:965-971` resolves `PagingPrototypeLayout` with `try?`, then uses `?? FileManager.default.temporaryDirectory` directly and installs a real `LayoutStoreActor`. With a normal no-profile launch, an error in the production resolver selects that fallback.
2. `Sources/AppGridUI/LayoutStore/LayoutStore.swift:139-144` calls the throwing `FileManager.default.url(for: .applicationSupportDirectory, ..., create: true)`. For example, inability to obtain/create that location can throw; there is no enclosing product-owned fallback directory at the call site.
3. `Sources/PagingPrototypeApp/AppDelegate.swift:3400-3404,3419-3428` immediately starts restoration and calls `store.load()`.
4. `Sources/AppGridUI/LayoutStore/LayoutStoreActor.swift:72-77,90-92` selects `FileManagerLayoutStoreIO` by default and loads initial state. `LayoutStoreActor.swift:268-289` creates/opens the supplied directory, attempts the lock, and calls `cleanupTempFiles()` even when lock acquisition failed.
5. `Sources/AppGridUI/LayoutStore/LayoutStoreActor.swift:372-375` enumerates `storeDirectory`, selects **all** names with suffix `.tmp`, and calls `removeFileIfExists` for each.
6. `Sources/AppGridUI/LayoutStore/LayoutStoreIO.swift:83-84,95-97` implements that enumeration with `FileManager.contentsOfDirectory` and deletion with `FileManager.removeItem`. It does not restrict deletion to the journal's two known temporary filenames or validate ownership.

**Policy conflict.** `Docs/ADR-009-WORKSPACE-LAYOUT-AND-PERSISTENCE.md:73-78` requires a dedicated Application Support subdirectory and expressly rejects `/tmp` as production persistence. `Docs/RELEASE_0.1.0_SPEC.md:21` forbids shipping a known data-loss defect merely to complete publication.

**Affected scope and consequence.** Normal production composition on the storage-resolution error path; unrelated removable `.tmp` files/directories immediately inside the returned temporary root can be removed during startup. Journal writes also target this shared, purgeable root, so a successful save receipt there cannot establish durable production layout storage. This review does not claim the resolver fails on a healthy installation or that any actual user file was deleted.

**Likely root cause.** A broad availability fallback passes an unowned directory to a store whose startup cleanup assumes exclusive namespace ownership.

**Recommended solution.** Main should obtain/record the bounded source/spec exception and make storage unavailability fail closed: retain usable in-memory presentation, surface unavailable/degraded persistence, and perform no journal I/O against a shared temporary root. Also restrict cleanup to recognized journal temporary artifacts in a verified, dedicated store directory. A temporary subdirectory alone would reduce collateral deletion but would still need an explicit durability policy; it would not justify describing temporary saves as durable production storage. Do not fix this merely with release-note wording or an assumption that the path is unlikely.

**Required regression evidence after an authorized repair.** Inject resolver failure in an owned synthetic environment, keep unrelated `.tmp` file and directory sentinels intact, prove no fallback-root journal/lock writes, verify truthful degraded/save/Quit behavior, and verify normal dedicated-directory persistence remains intact. Main owns execution and the fresh full suite/package hashes. Never reproduce this against the user's shared temporary directory.

**Regression risks.** Accidentally losing existing layout restoration, silently accepting nonpersistent changes, breaking termination protection, or removing intentional cleanup of interrupted journal writes. Keep test-profile isolation and the normal journal format unchanged unless explicitly specified.

**Confidence: high** in the static data-loss chain; frequency, actual OS resolver failure modes, and runtime reproduction are untested. The conditional trigger limits prevalence, not the release-blocking severity.

## Warnings and claims that remain untested

1. **Four-finger inward activation is default ON, not opt-in on first launch.** `ActivationPreferences.swift:29-45,151-155` explicitly implements the prior user decision; `Docs/FOUR_FINGER_ACTIVATION_SPEC.md:52-53` documents it. `LauncherRuntimeServices.swift:28-33` lazily attaches the real provider when enabled; a saved OFF remains device-free. Outward Hide is independently default OFF (`ActivationPreferences.swift:40-41,177-180`). Do not advertise all device/global functionality as default off. This review does not reinterpret the approved inward default as an unauthorized privacy change.
2. **Private touch ABI remains unsupported across future OS changes.** `MultitouchSupportBackend.swift:176-201` dynamically opens Apple's private system framework and casts symbols; `:673-683` reports unavailable/no-device when loading or enumeration fails. Missing symbols are handled, but symbol presence is not proof that the private ABI remains compatible. This is an explicit accepted limitation (`Docs/RELEASE_0.1.0_SPEC.md:20-21`), not proof of a missing third-party runtime or a new unconditional launch failure. No device/OS matrix, energy, raw-input privacy, or private-ABI acceptance was performed here.
3. **Unsigned distribution was chosen, not accidentally omitted.** The packaging script has no signing/notarization step and states that limitation (`Scripts/package-app.sh:3,307`). This is not itself a blocker under the explicit release contract. Compiler/linker ad-hoc signatures, Gatekeeper behavior, install location, and real `SMAppService` registration remain unverified; `LaunchAtLoginService.swift:113-125` exposes failures rather than guaranteeing registration. No system-security workaround is recommended.
4. **Historical policy documents are not complete current product descriptions.** `Docs/PRIVACY_DATA_MAP.md:1-6,61-62` is explicitly Phase 1B and describes an earlier non-global/non-writing scope. Later activation and optional activity contracts supersede that narrow scope: `Docs/ADR-012-SYSTEM-WIDE-ACTIVATION-PRIVACY.md:24` and `Docs/LIBRARY_LAUNCH_ACTIVITY_PROPOSAL.md:43-47`. Release text must describe current local stores, optional history, approved default touch behavior, and explicit Trash actions. The older privacy map alone cannot support a blanket current privacy statement.
5. **No legal clearance or license selection.** The script's narrow copy list reduces accidental reference/test-media inclusion but cannot establish provenance or redistribution rights for the application/icon/source. The report neither chooses a license nor certifies independent implementation/clean-room status. See the explicit boundary in `Docs/RELEASE_0.1.0_SPEC.md:7,21`.
6. **No artifact or public-release PASS.** Fresh complete tests, clean export, Release compilation, arm64/deployment target, packaged-language probe, marker/diagnostic metadata absence, linked libraries, archive exclusions/path safety, hashes, actual install/upgrade GUI behavior, tag/asset integrity, and GitHub stable-release status remain Main's independent gates (`Docs/RELEASE_0.1.0_SPEC.md:12-18`).
